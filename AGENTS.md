# AGENTS.md

Repo-specific guidance for OpenCode sessions working in this codebase.

## What this is

Fork of the Espruino Pixl.js firmware for an nRF52-based device whose primary use is Amiibo and NFC card emulation. Three independent components live in one repo:

- `fw/` — firmware for the nRF52832 (C, GCC/Make). Built from `fw/application` (app + softdevice) and `fw/bootloader` (secure BLE DFU bootloader).
- `web/` — device companion web UI (Vue 2 + Element UI + webpack 2, legacy). Published to `gh-pages/`.
- `hw/` — KiCad hardware (RevA/B/C boards + an OLED variant). Not built; reference only.

Docs are in `docs/{en,zh,it}/`. The authoritative build story is `docs/en/03-Build-Firmware.md` and the Makefiles — trust those over prose if they disagree.

## Build (firmware)

The firmware does NOT build on a host machine without the Nordic nRF5 SDK and the arm-none-eabi toolchain. Two supported routes:

1. Local (toolchain + SDK installed): source `fw/env.sh` first to set `GNU_INSTALL_ROOT`, `NRF52_SDK_ROOT`, and `PATH`, then build:
   ```bash
   source fw/env.sh
   cd fw && make all BOARD=LCD   # or BOARD=OLED
   ```
   `fw/env.sh` expects the ARM toolchain at `$HOME/tools/arm-gnu-toolchain-15.3.rel1-x86_64-arm-none-eabi/` and the nRF5 SDK at `$HOME/tools/nRF5_SDK_17.1.0_ddde560`. Do NOT use `-j` with `make all` — parallel sub-makes cause linker errors (the `make[2]:` jobserver messages leak into linker input).

2. Docker (recommended, matches CI): `docker run -it --rm solosky/nrf52-sdk:latest`, then inside:
   ```bash
   git clone https://github.com/solosky/pixl.js && cd pixl.js
   git submodule update --init --recursive
   cd fw && make all BOARD=OLED RELEASE=1     # or BOARD=LCD
   ```
3. CI: `.github/workflows/pixl.js-fw.yml` runs `cd fw && make all RELEASE=1 APP_VERSION=$GITHUB_RUN_NUMBER BOARD=${{matrix.board}}` on `develop` and `neo_v2` branches.

Key facts an agent would otherwise guess wrong:

- `BOARD` is `LCD` or `OLED`; it is a build-time define (`-DBOARD_$(BOARD)`), not a runtime choice. Default in `fw/application/Makefile` is `OLED`; in `fw/bootloader/Makefile` it is `LCD`.
- `NRF52_SDK_ROOT` must point at nRF5 SDK 17.1.0 (see `fw/docker/Dockerfile`). The Makefiles rely on it; without it nothing compiles.
- Submodules are required: `mlib`, `tlsf`, `cwalk`, `spiffs`, `littlefs`, `chameleon-ultra` (see `.gitmodules`). `git submodule update --init --recursive` is not optional.
- Top-level `fw/Makefile` runs `bl`, `app`, then `ota` (`make all` = bootloader + app + OTA zip). Outputs land in `fw/_build/`:
  - `bootloader.hex`, `pixljs.hex`, `pixljs_all.hex` (merged sd+bl+app), `pixljs_ota_v<APP_VERSION>.zip` (DFU package), `fw_readme.txt`, `fw_update.bat`.
- `make version` regenerates `application/src/version.inc.h` via `scripts/version_gen.py` (git-derived) and is invoked automatically by `default`/`all`.
- Flashing targets need `nrfjprog` (J-Link) or `openocd` (CMSIS-DAP, e.g. PWLink2 lite). `flash_ocd` / `flash_all_ocd` / `erase_ocd` are defined in `fw/application/Makefile`; VS Code build task runs `make all flash_openocd -j8`.
- Softdevice is `s112` 7.2.0; `flash_softdevice` programs it. `make full` merges settings + bootloader + sd + app via `mergehex`.
- OTA packages are signed with `fw/bootloader/priv.pem`; `bootloader/privgen` regenerates the DFU key pair. Don't commit a replacement `priv.pem` casually.

## Code generation (`make gen`)

Several C sources in `fw/application/src` are generated by Python scripts under `fw/scripts/` and MUST be regenerated when their data sources change — do not hand-edit the generated files:

- `amiibo_db_gen.py` → `amiidb/db_amiibo.c`, `db_game.c`, `db_link.c` (from `fw/data/{amiidb_amiibo,amiidb_game,amiidb_link}.csv`)
- `i18n_gen.py` → `i18n/*.c` and `i18n/string_id.h` (from `fw/data/i18n.csv`)
- `font_data_gen.py` → u8g2 font C files in `application/src/mui/` (from `fw/data/*.bdf`)
- `resource_gen.py` → app icons (from `fw/resources/`)
- `version_gen.py` → `application/src/version.inc.h` + `version.json`

Python scripts only need `imageio` (see `fw/scripts/requirements.txt`) plus stdlib.

## Firmware architecture notes

- Entry point: `fw/application/src/main.c`. UI uses u8g2 and an in-house "mui" framework (`src/mui/`, views in `src/mui/view/`, scenes per app under `src/app/*/scene/`). Apps are registered in `src/core/mini_app_registry.{c,h}` and launched via `mini_app_launcher`.
- App modules live in `src/app/`: `amiibo`, `amiidb`, `amiibolink`, `chameleon`, `ble`, `game`, `player`, `settings`, `desktop`. Each typically has `app_<name>.c`, `view/`, `scene/`.
- NFC/card emulation pulls code from the vendored `chameleon-ultra` submodule (`rfid/nfctag/hf/*`) — see `CHAMELEON_ROOT` in `fw/application/Makefile`.
- Amiibo crypto comes from `fw/components/amiitool` (vendored, not a submodule). `key_retail.bin` is NOT in the repo and not required to build; users upload it to the device root storage at runtime for full Amiibo features.
- VFS layer (`src/mod/vfs/`) supports both SPIFFS and LittleFS over external SPI flash (`vfs_driver_spiffs.c`, `vfs_driver_lfs.c`).

## Build variants and branches

- `BOARD=LCD` vs `BOARD=OLED` selects display driver defines; both are produced per CI run.
- Active development branch is `develop` (CI builds it and `neo_v2`); `main` exists but the workflow only triggers on `develop`, `neo_v2`, and tags. The bootloader Makefile defaults to `LCD` while app defaults to `OLED` — build both board kinds explicitly rather than relying on defaults when targeting a specific device.

## Web (`web/`)

- Legacy Vue 2.5 / webpack 2 / Element UI 2. `yarn` for deps; `npm run dev` (webpack-dev-server on :8010) and `npm run build`. Built artifacts are manually copied to `gh-pages/` and pushed via `git subtree push --prefix=gh-pages origin gh-pages`. There is no test/lint setup; the `web/README.md` release steps are the source of truth.
- `package-lock.json` and `yarn.lock` both exist — the repo's documented flow uses `yarn`.

## Code style

- `.clang-format`: LLVM base, 4-space indent (no tabs), `ColumnLimit: 120`, `Attach` braces, short `if` allowed. Match this when editing C.
- Keep `-Wall -Werror` commented out (it is intentionally disabled).

## Compiler warnings policy

Three tiers — applied in this order when a new warning appears:

1. **Fix first-party code** — If the warning originates in `fw/application/src/` (our code), prefer a proper code fix (const-correctness, forward declarations, explicit casts) over adding a `-Wno-*` flag.
2. **Suppress third-party code** — If the warning originates in submodules (`chameleon-ultra`, `mlib`, `tlsf`, `spiffs`, `littlefs`, `cwalk`, `qrcode`, `u8g2`, `amiitool`), in `app/chameleon/` (forked from upstream, treated as third-party), or in the Nordic SDK, **do not modify** that code. Suppress via `-isystem` (for headers) or a targeted `-Wno-*` in the Makefile.
3. **Last resort for first-party** — Only add a `-Wno-*` flag for first-party code when fixing the code would be more harmful or invasive than silencing the warning.

The Makefile's existing `-Wno-incompatible-pointer-types`, `-Wno-int-conversion`, and `-Wno-implicit-function-declaration` are legacy entries for third-party SDK noise — they are not a license to leave first-party code sloppy. New first-party warnings should be fixed, not masked.

## Things that are easy to get wrong

- Editing generated files (`db_*.c`, `i18n/*.c`, `version.inc.h`, font C files) — edit the data sources in `fw/data/`, `fw/resources/`, and re-run `make gen` (or the specific script) instead.
- Forgetting `git submodule update --init --recursive` — the build will fail on missing headers from `chameleon-ultra`, `mlib`, etc.
- Building outside Docker without `NRF52_SDK_ROOT` set — Makefile expands `$(SDK_ROOT)/...` to empty paths and fails confusingly.
- Treating `BOARD` as runtime config — it is a compile-time define baked into both bootloader and app; bootloader must be rebuilt for the same board as the app.
